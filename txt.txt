ПРАКТИЧЕСКАЯ РЕАЛИЗАЦИЯ СЕРВИСА СКАНИРОВАНИЯ ВЕБ-СЕРВИСОВ


ОБЗОР ПРОЕКТА

CyberScope – это интегрированная веб-платформа для автоматизированного комплексного анализа и разведки веб-сайтов. Платформа предназначена для пентестеров, администраторов безопасности, разработчиков и исследователей безопасности с целью упростить рутинные задачи сканирования на уязвимости, обнаружения скрытых ресурсов и сбора разведывательной информации.
Ключевые характеристики
–	Многофункциональность: Интеграция более 9 различных сканеров безопасности в единый интерфейс
–	Асинхронная обработка: Параллельное выполнение сканирований с использованием FastAPI и asyncio
–	Планирование задач: Встроенный планировщик для автоматизированных периодических сканирований
–	Управление отчетами: Генерация унифицированных отчетов в json и txt и docx форматах
–	REST API: Полный набор REST API эндпоинтов для программного взаимодействия
–	Telegram интеграция: Бот для управления сканированиями и отчетами через Telegram
–	Ответственное использование: Встроенные валидации для предотвращения сканирования внутренних адресов
Целевая аудитория
1. Пентестеры - для автоматизации рутинных операций разведки
2. SOC специалисты - для мониторинга безопасности корпоративных ресурсов
3. Разработчики - для проверки безопасности собственных приложений
4. Исследователи - для проведения научных исследований в области кибербезопасности

2.1. РАЗРАБОТАТЬ АЛГОРИТМЫ АНАЛИЗА ЗАЩИЩЕННОСТИ ВЕБ-СЕРВИСОВ

2.1.1 Выбор и обоснование ключевых метрик

Реализовано в проекте CyberScope через интеграцию 9+ сканеров безопасности:

А) Метрики на основе версионирования библиотек и фреймворков:
   • Wappalyzer Scanner (scanners/wappalyzer_scanner.py)
     - Детектирует 2000+ технологий (CMS, фреймворки, библиотеки, серверы)
     - Анализирует HTML, Meta теги, заголовки ответов, JSON ответы
     - База знаний с регулярными выражениями для идентификации версий
     - Результаты: технологии, версии, категории (Web Frameworks, CMS, Caching)
   
   • RetireJS Scanner (scanners/retire_scanner.py)
     - Специализированный на JavaScript библиотеках
     - Сравнение с базой данных известных уязвимостей (CVE)
     - Определение версий JS-зависимостей через package.json анализ

Б) Метрики на основе заголовков безопасности:
   • Vulnerability Scanner (scanners/vulnerability_scanner.py)
     - Проверка наличия основных заголовков: X-Frame-Options, X-Content-Type-Options
     - Анализ Content-Security-Policy, X-XSS-Protection
     - Оценка уровня защиты по шкале критичности (Critical, High, Medium, Low, Info)
   
   • SSL/TLS Scanner (scanners/ssl_tls_scanner.py)
     - Анализ сертификатов (срок действия, валидация цепи, алгоритм подписи)
     - Проверка версий протокола (TLS 1.2, 1.3 vs устаревших SSLv3)
     - Оценка шифров и алгоритмов на соответствие NIST/OWASP стандартам

В) Метрики кодов ответов сервера:
   • Web URL Scanner (scanners/web_url_scanner.py)
     - Анализ HTTP статус-кодов (200, 403, 404, 500 и т.д.)
     - Паттерны ответов для определения типа сервера и версии
     - Обнаружение скрытых директорий и файлов через перебор wordlist

Г) Информационные метрики:
   • DNS Scanner (scanners/dns_scanner.py)
     - MX, A, AAAA, CNAME, TXT, SOA записи
     - DMARC политики (dkim, spf, dmarc)
     - Риск-анализ DNS конфигурации
   
   • Whois Scanner
     - Информация о регистранте и владельце домена
     - Сроки регистрации и обновления
     - Исторические данные о регистрациях

2.1.2 Определение базы знаний для определения версий CMS и фреймворков

База знаний реализована на основе:

А) Встроенная база технологических паттернов (utils/technology_patterns.py):
   • Регулярные выражения для следующих CMS:
     - WordPress: по параметрам wp-*, wp-content, wp-json, версиям плагинов
     - Joomla: по файлам конфигурации, версиям компонентов
     - Drupal: по characteristic файлам, API эндпоинтам
     - Magento: по layout файлам и версиям extension
     - OpenCart, Prestashop и другие
   
   • Паттерны для веб-фреймворков:
     - Django: по structure файлов, CSRF token, csrf middleware
     - Flask: по werkzeug signature в ошибках

     - ASP.NET: по aspx extension, ViewState параметрам
     - Java Spring: по структуре WAR архива, конфигам

Б) Интеграция с Wappalyzer:
   • Использует открытую базу данных технологий от Wapplalyzer
   • Постоянно обновляемый репозиторий с 10000+ сигнатурами
   • Категоризация: 80+ категорий технологий
   • Пример: обнаруживает jQuery 3.6.0 по function $, window.jQuery версия из source

В) NVDLIB интеграция (requirements: nvdlib):
   • Подключение к National Vulnerability Database (NVD)
   • Получение CVE данных по идентифицированным компонентам
   • Сопоставление версий с известными уязвимостями

2.1.3 Разработка алгоритмов сопоставления сигнатур для определения стека технологий

Реализовано многоуровневое распознавание:

А) Уровень 1: Анализ заголовков HTTP ответов
   ```python
   X-Powered-By: PHP/7.4.3      # Определение сервера
   Server: Apache/2.4.41        # Версия веб-сервера
   X-AspNet-Version: 4.0.30319  # ASP.NET версия
   Wappalyzer-By: ...          # Wappalyzer результаты
   ```

Б) Уровень 2: Анализ HTML контента и meta-данных
   • Parser на BeautifulSoup для:
     - Поиска CMS indicators (wp-json, /joomla/)
     - Анализ комментариев в коде
     - Версии из meta-тагов (meta name="generator" content="WordPress 6.2")
     - JavaScript источники и версии

В) Уровень 3: Регулярные выражения и паттерны
   • Для каждой технологии: набор regex для:
     - URL паттернов
     - HTML элементов
     - Ошибок и exception messages
     - Конфигурационных файлов
   • Примеры из кода:
     - WordPress: /wp-admin/, wp-content/plugins
     - Drupal: modules/, themes/, drupal.settings.js
     - Django: django.setup(), {% csrf_token %}

Г) Уровень 4: Анализ ответов от специфических endpoints
   • GET /api/v1/version → JSON с версией
   • GET /.well-known/security.txt → информация о безопасности
   • HEAD запросы для определения сервера без загрузки HTML

Д) Уровень 5: Анализ статиков (CSS, JS)
   • Wappalyzer и retire.js анализируют JavaScript файлы
   • По URL, содержимому, именам функций определяют библиотеки
   • Пример: /jquery-3.6.0.min.js → jQuery 3.6.0

2.2. СПРОЕКТИРОВАТЬ АРХИТЕКТУРУ ВЕБ-СЕРВИСА

2.2.1 Архитектура системы: микросервисы или монолит

Выбор: ГИБРИДНЫЙ ПОДХОД с элементами микросервисов

А) Компоненты архитектуры:

   I. BACKEND (FastAPI монолит с модульной структурой)
      
      1. API Gateway (server.py)
         • FastAPI приложение на порту 5000
         • CORS middleware для поддержки фронтенда
         • REST эндпоинты для управления сканированиями
         • Stream response для real-time логирования
         • Воидация IP адресов (предотвращение сканирования localhost, 127.0.0.1)
      
      2. Плановщик задач (scheduler.py)
         • Фоновый процесс (threading.Thread)
         • Загрузка/сохранение задач в JSON (scheduled_tasks.json)
         • Периодическое выполнение запланированных сканирований
         • Интеграция с asyncio для асинхронных операций
         • Поддержка callback функций для каждого типа задачи
      
      3. Модульная система сканеров (scanners/)
         • Каждый сканер - независимый модуль Python
         • Интерфейс: функция simple_scan() и главный класс
         • Асинхронная обработка параллельного выполнения
         
         Сканеры в проекте:
         • vulnerability_scanner.py - XSS, SQLi, заголовки безопасности
         • wappalyzer_scanner.py - идентификация технологий
         • osint_scanner.py - разведка открытых данных
         • web_url_scanner.py - сканирование директорий/файлов
         • retire_scanner.py - JavaScript уязвимости
         • cors_scanner.py - CORS конфигурация
         • ssl_tls_scanner.py - сертификаты и протоколы
         • dns_scanner.py - DNS записи и конфигурация
         • nmap_scanner.py - портсканирование (NMap интеграция)
         • nuclei_scanner.py - шаблонные уязвимости
      
      4. Система отчетов (core/report_utils.py)

   II. FRONTEND (React + SCSS)

      • Взаимодействие с backend через REST API
      • Real-time логирование через Server-Sent Events (SSE)

2.2.2 Алгоритмы поиска и валидации поддоменов (DNS resolution, HTTP probe)

А) DNS Resolution (scanners/dns_scanner.py)

   Этапы:
   1. Попытка получить основные DNS записи:
      • A record (IPv4) - основная запись
      • AAAA record (IPv6) - поддержка IPv6
      • MX records - почтовые серверы
      • CNAME - каноничное имя
      • SOA - информация о зоне
      • TXT records - текстовые записи (особенно SPF, DMARC)
   
   2. Анализ DMАRC политики:
      • SPF (Sender Policy Framework) - авторизация отправителей
      • DKIM (DomainKeys Identified Mail) - подписи писем
      • DMARC (Domain-based Message Authentication) - агрегированная политика
   
   3. Обработка ошибок:
      • NXDOMAIN - домен не существует
      • Timeout - сервер не отвечает
      • SERVFAIL - ошибка сервера
   
   Реализация: использование pydig для параллельный запросов

Б) HTTP Probe (scanners/web_url_scanner.py)

   Алгоритм:
   1. Валидация URL:
      • Проверка формата (http://, https://)
      • Попытка обе схемы (http и https)
      • Разрешение редиректов (follow redirects)
   
   2. Тестирование connectivity:
      • HEAD запрос для быстрой проверки
      • Анализ response кодов и headers
      • Таймауты для долгих ответов (по умолчанию 10-30 сек)
   
   3. Обнаружение скрытых ресурсов:
      • Перебор common.txt словаря (wordlists/common.txt)
      • Параллельное тестирование (ThreadPoolExecutor)
      • Правила для фильтрации 404 ответов
   
   4. Анализ результатов:
      • Статус коды: 200 (OK), 301/302 (Redirect), 401/403 (Auth), 500 (Error)
      • Размер контента для обнаружения скрытых страниц
      • Время ответа для определения брутфорса
   
   Определение поддоменов через:
   • DNS enumerations - AXFR zone transfer если возможен
   • Certificate Transparency logs - поиск в CT базах
   • Common wordlist перебор
   • Интеграция с OSINT сканером для открытых данных

В) Комбинированный подход валидации

   1. Параллельное выполнение всех проверок
   2. Кэширование результатов для избежания дубликатов запросов
   3. Обработка ошибок и timeout'ов с retry логикой
   4. Логирование всех попыток для отладки

2.2.3 Механизмы проверки уязвимостей (SQLi, XSS, анализ заголовков)

А) XSS (Cross-Site Scripting) Detection

   Реализация в: scanners/vulnerability_scanner.py, utils/xss_payloads.py
   
   Методология:
   1. Определение инъекционных точек:
      • Query параметры: ?search=<payload>
      • Path параметры: /user/<payload>/profile
      • POST данные: form fields, JSON body
      • Cookies: Set-Cookie manipulation
      • Headers: User-Agent, Referer
   
   2. Набор тестовых payload'ов (из utils/xss_payloads.py):
      • Простые: <script>alert(1)</script>
      • Кавычка: "><script>alert(1)</script>
      • Event handlers: <img src=x onerror=alert(1)>
      • SVG: <svg onload=alert(1)>
      • Обход фильтров: <<script>alert(1)</script>
   
   3. Методы тестирования:
      • Reflected XSS: отправка payload в параметр, проверка в response
      • DOM-based: анализ JavaScript кода для опасных операций (eval, innerHTML)
      • Stored XSS: если есть форма, сохранить payload и проверить отражение
   
   4. Анализ результатов:
      • Проверка payload'а в исходном коде страницы
      • Отсутствие экранирования (>< не преобразованы в &lt;&gt;)
      • Наличие типа контента Content-Type: text/html

Б) SQLi (SQL Injection) Detection

   Реализация: utils/sql_payloads.py
   
   Стратегия:
   1. Определение параметров с потенциалом SQL:
      • id параметры: /product?id=<payload>
      • search: /search?q=<payload>
      • Поля форм логина
   
   2. Payload'ы для тестирования:
      • Boolean-based: ' OR '1'='1 (истина) vs ' OR '1'='2 (ложь)
      • Time-based: ' OR SLEEP(5)-- - задержка ответа означает уязвимость
      • Union-based: ' UNION SELECT NULL,NULL-- - количество колонок
      • Error-based: ' AND EXTRACTVALUE(1,CONCAT(0x7e,version())) - ошибки БД
   
   3. Методология:
      • Анализ разницы в ответах между payload'ами
      • Временные характеристики для time-based SQLi
      • Обработка исключений и ошибок БД в ответах
   
   4. Обнаружение:
      • Ошибки MySQL: "You have an error in your SQL syntax"
      • PostgreSQL: "ERROR: syntax error"
      • SQL Server: "Unclosed quotation mark"

В) Проверка заголовков безопасности

   Реализация в: scanners/vulnerability_scanner.py (check_security_headers)
   
   Ключевые заголовки и их значение:
   
   1. Content-Security-Policy (CSP)
      • Ограничивает источники для script, style, image и др.
      • Отсутствие = HIGH риск XSS атак
      • Проверка: есть ли 'none' или strict-dynamic
   
   2. X-Frame-Options
      • DENY - невозможно встроить в iframe
      • SAMEORIGIN - только с того же источника
      • Отсутствие = HIGH риск Clickjacking
   
   3. X-Content-Type-Options: nosniff
      • Предотвращает MIME type sniffing
      • Критично для предотвращения XSS через uploaded files
   
   4. X-XSS-Protection: 1; mode=block
      • Активирует XSS фильтр браузера (legacy)
      • Заменяется на CSP в современных браузерах
   
   5. Strict-Transport-Security (HSTS)
      • max-age указывает период HTTPS enforcement
      • includeSubDomains - применяется ко всем поддоменам
      • Отсутствие = MEDIUM риск для HTTPS downgrade attacks
   
   6. Referrer-Policy
      • no-referrer, strict-origin-when-cross-origin и др.
      • Контроль утечки информации
   
   7. Permissions-Policy (ранее Feature-Policy)
      • Ограничение доступа к API (camera, microphone, geolocation)
   
   Алгоритм оценки:
   ```
   Критичность = CRITICAL если:
     - Нет CSP и нет X-Frame-Options
   Критичность = HIGH если:
     - Нет одного из: CSP, X-Frame-Options, X-Content-Type-Options
   ```

Г) Анализ SSL/TLS (scanners/ssl_tls_scanner.py)

   1. Проверка версии протокола:
      • TLS 1.3 - современный стандарт (GOOD)
      • TLS 1.2 - приемлемо (MEDIUM)
      • TLS 1.0/1.1 - DEPRECATED (CRITICAL)
      • SSLv3 и ниже - CRITICAL уязвимость
   
   2. Анализ сертификатов:
      • Валидность (not before / not after)
      • Subject CN (Common Name) соответствует доменному имени
      • Цепь сертификатов (Chain of Trust)
      • Self-signed сертификаты (потенциальный MITM)
   
   3. Проверка шифров:
      • Слабые: DES, RC4, MD5 (CRITICAL)
      • Средние: AES-128 (MEDIUM)
      • Сильные: AES-256, ChaCha20 (GOOD)
   
   4. Известные уязвимости:
      • Heartbleed (CVE-2014-0160) - версия OpenSSL
      • POODLE - SSLv3 fallback
      • CCS Injection - непроверенные CCS пакеты

2.2.4 Процедуры формирования отчета (визуализация данных, уровни критичности)

А) Система уровней критичности

   Определены 5 уровней:
   1. CRITICAL (красный) - требует немедленного исправления
      • Примеры: публичная RCE, SQL injection, открытая админ панель
      • SLA: исправить в течение 24 часов
   
   2. HIGH (оранжевый) - значительная угроза
      • Примеры: reflected XSS, отсутствие основных заголовков, слабое шифрование
      • SLA: исправить в течение 72 часов
   
   3. MEDIUM (желтый) - умеренная угроза
      • Примеры: устаревшие библиотеки, информационное раскрытие, слабая конфигурация
      • SLA: исправить в течение 2 недель
   
   4. LOW (синий) - минимальная угроза
      • Примеры: комментарии в коде, неоптимизированные настройки
      • SLA: план исправления не требуется
   
   5. INFO (белый) - информационное
      • Примеры: версии технологий, трудно эксплуатируемые проблемы
      • Документирование для справки

Б) Структура отчета

   1. JSON формат (reports/{scanner}/json/)
      ```json
      {
        "scan_info": {
          "target": "example.com",
      ```

   ```bash
   # Клонирование репозитория

   bash install-tools.sh

   pip install -r backend/requirements.txt
   npm install --prefix frontend/

   apt-get install nmap whois dnsutils  # Ubuntu
   brew install nmap whois dig          # macOS
   ```

   • Создать .env файл с параметрами
   • Настроить TELEGRAM_BOT_TOKEN если нужна интеграция

2.4.2 Рекомендации по настройке параметров сканирования

А) Параметры глубины сканирования

1. QUICK MODE (быстрое)
   • Активные сканеры: wappalyzer, dns, web_headers
   • timeout: 30 сек на сканер
   • Пропуск: nmap, nuclei, retire (долгие)
   • Время выполнения: 2-5 минут
   • Использование: CI/CD пипелайны, мониторинг

2. STANDARD MODE (стандартное) - DEFAULT
   • Активные сканеры: ВСЕ кроме nuclei (если требует много времени)
   • timeout: 60 сек на сканер
   • Параллельные задачи: 4-8
   • Время выполнения: 10-20 минут
   • Использование: регулярные аудиты

3. DEEP MODE (глубокое)
   • Активные сканеры: все включение nuclei, osint
   • timeout: 120-180 сек на сканер
   • Параллельные задачи: 2-3 (меньше для стабильности)
   • Перебор дополнительных wordlist'ов
   • Время выполнения: 30-60+ минут
   • Использование: pen testing, research

Б) Параметры таймаютов

• Детектированию и классификации уязвимостей
